# Self-hosted inference: correlated request-phase observability (offline)

**Base:** `209e0999e84b91b28805be652366efefe63e7640` (R5dj), 2026-10-28. **Scope:** diagnostic-only, opt-in. **Local-model evaluation remains CLOSED:** `LOCAL ACCEPTANCE BLOCKED BY RUNTIME RELIABILITY`. No model inference, provider restart, SSH modification, endpoint change, prompt/policy change, retries or acceptance conducted. The older `inference-30` receipt is immutable: this patch does **not** retrospectively determine Ollama receipt or stall cause.

## Phase contract and evidence strength

| Phase / requested signal | Future Clack observation | What the observation **actually** proves |
|---|---|---|
| Agent generation / provider deadline | Optional `generationId` (UUID), `sessionId`, `runId`, `attempt`, `deadline-start`, `deadline-clear`, `deadline-fire`, `parent-abort-propagated`, `settled` | Agent JavaScript state; does not imply native dispatch |
| Native WebView bridge | Signal-bound `native-id-linked`, `native-ipc-start`, `native-parent-abort`, `native-cancel-ipc`, `native-response-headers`, `native-first-chunk`, `native-settled` | Native child ID and WebView events, including when cancellation was issued |
| Native IPC and Clack admission | Existing admission observations plus `native-ipc-ready` recorded **after** native ownership/SSH pin/validation but **before** Clack admission/preflight | Clack accepted a native command; **not** Ollama scheduler admission |
| URL safety / resolver | `resolve-start`, `resolve-end` | Resolution / IP classification complete; not a socket connect |
| HTTP client | `http-client-build-start`, `http-client-ready`, `request-built` | New reqwest client and request builder prepared; **not** bytes written |
| Connect + HTTP request write + response-header wait | `send-await-start`; terminal error classification (`connection-failed`, `connect-timeout`, `first-output-timeout`, etc.), and `lastRequestStage` | Entry to combined reqwest send future. **Cannot split physical connect, upload, header wait** without additional supported instrumentation |
| Response headers/status | Existing `headers` + new numeric `httpStatus` (no header values in diagnostic trace) | `reqwest.send()` returned an HTTP response |
| First body read / streaming | `first-body-chunk`, `body`, `meaningful-progress`, IPC forward/reject; `bodyChunks`, `bodyBytes`, `lastBody`, `lastForwarded` | First decoded HTTP transfer-body chunk **delivered by reqwest**, not an OS socket read or first model token |
| Provider protocol completion / EOF | Existing `provider-done`, `eof`, `completed` | Completion marker seen by Clack's parser, HTTP EOF if separately observed |
| Cancellation/terminal | `cancellation-observed`, `deadline-observed`, `transport-error` plus `failureCode`, retained `lastRequestStage` | Clack native lease ended; **not** proof remote runner cleaned up |
| Ollama arrival, admission, scheduler, runner, GPU | **Not observable in Clack alone** | Requires provider-side service logs/trace or a separate controlled diagnostic boundary |

`first-body-chunk` is the first non-terminal body chunk returned by `reqwest` (it can include non-generative metadata). This is deliberately distinct from SDK `first-meaningful-output`. `httpStatus`, `lastRequestStage` and internal `failureCode` are bounded, content-free metadata, while the existing `headers` IPC payload is necessary for ordinary HTTP semantics and is **not** copied into the trace. Diagnostics do not record prompts, tool input, generated text, headers, tokens, request bodies, raw URLs, credentials, SSH keys or provider exception text. `lastRequestStage` is a *last observed application marker*: in the absence of headers it will typically be `send-await-start`, not a guessed TCP phase.

## Correlation contract

The optional Agent phase observer produces a fresh `generationId` for each SDK provider-wrapper invocation, with `attempt:0` for its first underlying `doStream` call; internal retries increment the ordinal and receive **new native request IDs** while retaining the same generation ID. The wrapper's abort signal is used as an in-memory `WeakMap` key; the native WebView proxy receives exactly this signal through the Ollama adapter and reports the child ID allocated by `ai_http_open`. This creates an explicit generation → attempt → native request join **without** changing provider requests or adding HTTP headers. Every recovery observation includes `generationId`, attempt number, optionally native ID, and latest genuinely seen WebView transport stage. The existing native trace, parser failure observer, cancellation provenance, and admission observations already use the **same native request ID**. Thus a report can join them by ID, not timestamps.

A separate, opt-in `installSelfHostedInferencePhaseObserver()` may record `{sessionId,runId,provider,modelRef,digestRef?,runtimeEpochRef?,event}`. `modelRef` and `digestRef` are **captured profile references**, and `runtimeEpochRef` is the *calibration proof scope* stored in the profile, not a new daemon identity probe. It must be compared against independently captured runtime/provider evidence before calling it current. When preflight has already parsed the selected Ollama request, only validated, bounded scalar `contextTokens` (`num_ctx`), `outputTokens` (`num_predict`) and `toolSchemas` count are exposed as a `native-controls-prepared` diagnostic; this does not retain or reparse prompt content. This observer is not installed in normal production. The existing `onProviderRecoveryPhase` callback continues to work. The in-memory signal mapping is detached on normal settlement; after parent deadline it remains weakly associated until the native cancellation settlement arrives, if one arrives, so the final cleanup can still be joined. A direct or non-Agent inference without the wrapper has a native ID but **no invented Agent generation ID**. Cancellation before native allocation has a generation ID but legitimately no native child ID. Repeated/overlapping sessions never rely on wall-clock proximity to disambiguate requests.

If a future operator wants durable receipts, install the observer in a purpose-built isolated diagnostics host with explicit opt-in, request-ID allowlist, a per-run capped ring buffer, failure-triggered persistence only, an exclusive output path, strict file permissions and automatic expiration. Native `AcceptanceDiagnostics` is already debug-build-only and absent without its explicit installed state, with a bounded event deque. There is **no new always-on telemetry**, network transmission or persistent store here. The new `trace` metadata fields do not depend on the optional Agent hook.

## What the current reqwest transport cannot reveal

`build_safe_client` creates a **new** client on each request. Therefore cross-request pooled keepalive reuse is not present in the current HTTP inference execution; reqwest may still reuse a connection within its own request/redirect handling. The client pins its resolver to approved IP addresses and uses a bounded connect timeout. Debug diagnostics now record only an intended `destinationPort` and coarse `resolvedIpScope` (`loopback`, `private`, `public` or `mixed`) after validated resolution, never a raw hostname or IP. They do **not** establish which candidate address was dialed. The endpoint URL identifies the *intended destination*; a localhost port-forward denotes the tunnel listener, **not** Ollama's remote destination or successful SSH forwarding. This patch does not log raw destination IPs/hosts (which can expose private endpoints), nor claim connect or write boundaries.

Reqwest's public `RequestBuilder::send().await` combines connector, TCP/TLS handshake, request transmission, and response-header wait. Its ordinary error flags can classify a failure (`is_connect`, `is_timeout`) but cannot time successful subphases. Recording `send-await-start` as `connect-start` or `request-write-complete` would be false. To obtain genuine socket phases in a *separately authorized* effort, evaluate supported reqwest/hyper connection tracing with an unchanged connector and validated noninterference, or instrument a transparent diagnostic boundary. Never swap connector/transport or weaken DNS pinning, safety, timeout, redirection or connection behavior solely for observability.

## Smallest practical Ollama-side correlation design (not deployed)

1. First check whether the **installed Ollama version** emits request arrival, scheduler enqueue/admission, model load/eviction, runner assignment/execution, provider error and request completion with an *existing correlatable ID*. Document the exact log schema, clock source, enablement and redaction before enabling debug logs; provider text/logging may include sensitive material. Correlate a sanitized request ID only if the specific server actually propagates it. No assumption is made here about Ollama's log support.
2. If existing logs cannot distinguish arrival vs scheduling, design a **disabled-by-default LOCAL diagnostic HTTP boundary**, hosted on loopback and tested *entirely offline* with a synthetic server. It would record `client-arrival`, `upstream-connect`, `upstream-write-start`, `upstream-write-complete` where genuinely observable, `upstream-response-headers`, `upstream-first-body`, `upstream-Eof/error/cancel`. It would use bounded, content-free records and a mapping from Clack's `nativeRequestId` to the inbound request; an explicit out-of-band mapping or supported trace header requires a separate authorization and proof that it is inert. No request content, tool schemas or generated bytes would be persisted.
3. The boundary must preserve request method/path, body byte-for-byte, headers, streaming and cancellation, response status/headers, content encoding, backpressure, HTTP framing/proxy behavior and deadline behavior. Prove with synthetic end-to-end tests including large uploads, chunked streams, early disconnects, half-close, concurrent requests and delayed headers. Compare with direct transport and fail closed on unexpected differences. **Do not** deploy the proxy, change the endpoint or inject headers under this task. Even observing an upstream write only proves handoff to the upstream socket: it is not by itself evidence of Ollama's scheduler admission or runner execution.
4. A genuine provider-side `request-received → scheduler-enqueued → runner-started → runner-first-token → finished/cancelled` trace must be recorded inside Ollama or a supported runtime instrumentation facility. If unavailable, those stages must remain `unknown`, even when local upstream HTTP timing exists. Clack's native admission is exclusively its own capacity gate.

## Bounded future resource snapshots (design only)

At `native-id-linked`, prior to upstream send, at upstream receipt/queue/runner transitions (if supported), at first output, every ~5 seconds during a long wait, and at completion/cancellation, collect an optional **sample**, correlated to generation/native ID and runtime epoch, with monotonic + wall timestamps and explicit per-field availability. Keep at most 512 samples/request, default disabled; automatic sampling must be separately authorized and measured for overhead. A local sampler must not issue generation endpoints, load/evict models, restart the tunnel/daemon or alter the model profile.

Suggested fields: sanitized Ollama PID, uptime, CPU/RSS/status; runner PID and child process state; `/api/ps` loaded model/digest/context/expiration **at sample time only**; GPU device ID and used/total VRAM/utilization from available read-only driver telemetry; host MemAvailable/commit, swap used and page-in/out counters, OOM-kill/process-restart journal events and model load/eviction log markers. Associate each source with host, sampling timestamp, clock offset, units, collection failure and permission status. Avoid environment variables, command lines, model prompts, process arguments, keys or unbounded logs. `/api/ps` can identify a loaded context at its own timestamp but cannot retroactively prove a stalled request was admitted. No snapshot on its own proves resource pressure; demand temporal co-occurrence with queue/runner stalls and corroborating OOM/allocation or scheduling events.

## Next narrow decision (not authorization)

The **next** experiment, if separately approved, should exercise a single deliberately benign, finite *synthetic local HTTP responder* through the instrumentation and a separate opted-in provider-side log/diagnostic collector; only when that proves byte-preserving phases should any future inference be considered. Synthetic transport can distinguish Clack IPC/cancellation faults from local TCP/header handling. With genuinely correlated remote Ollama logs/runner marks and time-aligned GPU/host data, a later authorized inference could distinguish SSH/TCP, provider scheduler, runner and resource pressure. Until then those categories cannot be isolated from a zero-header stall.

**Strategic ordering:** **A** (remain on Ollama only after improving its *measurable* reliability/observability) is the narrowest near-term path. **C** (stronger remote model as a separate Clack end-to-end control) is a sensible independent later diagnostic; **B** (alternate local runtime) becomes attractive if Ollama remains unobservable/unreliable; **D** (hardware upgrade) requires evidence of a hardware limit, which R5di did not provide. None of A/B/C/D is authorized to execute here. No Muse, other local model, ForgeBoard or acceptance run.
