## Finding A — B1 fallback versus dispatch authorization

**Confirmed safety defect, not a B1 budget bypass.** B1 deliberately permits an appropriately small request when the provider has no verified large allocation. The original native callback refreshed its snapshot, independently rechecked settings identity, measured budget and reasoning, but never rechecked the already serialized Ollama context against **that final snapshot**. With `num_ctx=65536`, native proof initially matched and `maxOutput=128`, a concurrent change to loaded 4096 or disappearance of the loaded allocation could still receive **approved:true**; with the original output 2048 B1 independently blocked the request for size. Disabling B1 or raising required output would therefore conceal rather than correct the underlying authorization gap.

**Correction:** `requestPreflight` now compares the **actual serialized model/context** to the current post-refresh Ollama runtime target in the final pre-dispatch native ACK callback, not only during original `prepare()`. `runAgentStream` transmits the same-run accepted logical-continuation context as an immutable `requiredRuntimeContext` through `buildConfiguredLanguageModel` / the real provider preflight. For pinned continuations, final admission additionally demands the **current** provider snapshot's calibrated numeric trust (`snapshotContext`) equals that exact context (fresh loaded context/allocation, endpoint/digest, calibration, runtime epoch/version and reasoning identity). It checks identity again after the asynchronous checks before returning the native ACK. Invalid or missing current allocation fails closed with no HTTP dispatch; a legitimate small unpinned B1 request with no `num_ctx` still passes its existing conservative route, subject to the normal budget/identity protections. The existing one-time pre-stream check remains defense-in-depth, not an authority at final dispatch.

## Finding B — confirmed Automatic alternative at natural continuation

**Confirmed false rejection.** R5w's context pin had considered only `profile.toolVerification` (default), whereas a verified and independently confirmed `agentToolConfigurations` record may be the actual selected Automatic alternative, e.g. None / `think:false`. The same-run captured reasoning metadata ages after 30 seconds, even while tool proof, confirmation and the reasoning identity remain in their existing separate validity windows.

**Correction:** the context pin now searches original default and supported **confirmed alternative records** and selects only the record that the production `automaticAgentRecommendation` qualifies at **its own** native proof context. No default-to-alternative proof transfer. At logical continuation, fresh, model/digest/endpoint/revision-matched, 30-second-valid reasoning-control metadata may be read from the **existing native provider cache** solely to revalidate supported choices. Overlay is allowed only if an original captured record was already eligible under its original scope and proof; if its reasoning identity, epoch, model, endpoint, proof or confirmation was stale/changed, this metadata cannot revive it. The provider preflight independently revalidates the chosen explicit control at the actual request boundary. The original captured state and saved profile remain unchanged.

`transport.ts` additionally retains the actual accepted tool-record ID **and** reasoning variant only within its existing same-run/same-model ephemeral preparation. `agent.ts` rejects an unexpected record/variant switch between logical batches. A different run, model or restarted transport cannot inherit that record, and no proof or confirmation TTL is extended. Automatic defaults, explicit user choices, F1, permissions, output allowances, safety margins, budgets, deadlines and cloud-fallback policy are unchanged.
