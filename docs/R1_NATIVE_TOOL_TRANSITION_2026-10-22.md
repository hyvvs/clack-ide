## Wire/tool, normalization, prompt and history analysis

1. **F1 / schemas:** Raw `inference-17` through `inference-22` requests have the same serialized 14-tool schema list. Required coding tools are present, and each request has `think:true`, `options.num_ctx=65536`, `options.num_predict=2048`, `stream:true`, and one leading system message. No capability reduction, tool omission, different tool name, forced thought setting, context-block or safety margin failure coincides with request 19. Source: `src/modules/ai/lib/toolExposure.ts`, `toolObjective.ts`, `ollamaModel.ts:116-165`; raw requests and `scripts/audit-checkpointed-nemotron.mjs:60-74`.
2. **First transition prompt:** Both requests 18 and 19 contain the same **7,205-character system**. Neither `inference-19`'s system nor its 20 incoming message records contain `<tool_call>`, `<function=`, or `</think>` syntax. The preceding history contains real SDK/Ollama `assistant.tool_calls` and matching `tool` replies, including `call_ilruqg8d`. Textual pseudo-tool syntax first appears in **generated response content** in ID19. Source capture: raw requests and stream chunks. This rules out an earlier *textual* draft self-priming the first transition.
3. **Adapter mapping:** `src/modules/ai/lib/ollamaModel.ts:169-239,355-409` parses raw `message.tool_calls` into SDK `tool-input-*`/`tool-call` events and raw `message.content` into `text-*` events, independently of `message.thinking`. The raw ID18 structured call is present and executed; the raw ID19 frames lack any structured call. SDK cannot promote raw `<tool_call>` content to executable tools, and neither should Clack. The data do **not** support a lost structured call in Ollama transport, SDK interpretation or Clack normalization. Ollama-native `toolChoice` cannot force a call (`ollamaModel.ts:252-263`).
4. **Continuation prompt changes:** The first textual transition (18→19) occurs **before** any D2 length-continuation instruction. Starting at request 20, `answerContinuation.ts:1015-1029` adds the built-in instruction to continue the same assistant answer, and appends the exact preceding text as a new assistant message. The merged native system text grows from 7,205 characters (18/19) to 7,441 (20), 7,677 (21), and 7,913 (22), an additional 236 characters per continuation. This repetition is observable and could consume prompt space, but it cannot cause the *initial* ID19 switch and no consequential bug from repetition is demonstrated here. Do not change continuation policy on that inference alone.
5. **Prior draft influence:** Response 19 ended with an incomplete *semantic* `<tool_call>` draft, even though its NDJSON stream had no truncated transport frame. Its exact text, then response 20's exact text, were passed as raw assistant content into subsequent requests. Request 20's content includes a literal `</think>` in ordinary text, request 21 likewise carries such formatting. This may explain why later generations continued pseudo markup, but does not isolate model behavior from its inference engine/template. **No failed or truncated textual draft preceded request 19**; all previous mission tools were successful native operations. The report's 8,390 estimated older-draft tokens and 4,231 estimated current-partial tokens are marginal history costs, not safe deletion credit.
6. **Capacity and checkpointing:** Requested context remains 65,536, with 2,048 output reserve. Provider prompt evaluation counts for requests 18/19/20/21 are 9,135 / 10,659 / 12,759 / 14,870 respectively; these are not B1 estimates. The maximum native serialized B1 required budget was **39,932**, leaving **25,604** headroom on request 22; no pressure or eligible overwrite existed, and checkpoint projection/receipts/savings were zero. The model repeatedly reached the **output length cap**, not the context limit.

## Independent 120-second continuation-clock audit

The owning implementation is `src/modules/ai/lib/answerContinuation.ts`, `ANSWER_LIMITS.milliseconds=120_000` (lines 27–36). The first initial `doStream` executes before a continuation timer exists (lines 550–583). After a confirmed `length` finish, lines **973–980** record `continuationStarted=Date.now()` and arm a **single** `AbortController` deadline for the remaining cumulative time; it is not restarted on later length segments. Lines **583–590** calculate the elapsed time, lines **1031–1069** bound continuation preparation/dispatch by the combined abort signal, and lines **1072–1106** record an incomplete result and clean up.

The first length segment ended at **00:36:04.382**. The next request dispatched at **00:36:04.502**, and the timer therefore began between those events; the recorded cancellation at **00:38:04.386** is consistent with expiry 120 seconds after the first length finish. The third continuation's native dispatch had only about **0.5 seconds** of that window remaining, so its zero bytes **do not establish a stalled engine**. This was not the native per-request 600-second deadline, pre-output timeout or the harness 90-minute bound. `answerContinuation.test.ts` covers the deadline during stalled preparation and preservation of the cumulative limit across resumed answers.

**Causal distinction:** The first and subsequent unexecuted draft responses each exhausted 2,048 output tokens and returned `length`, which legitimately requested same-answer continuation. Thus the *textual output* led to additional length-based work and consumption of the continuation budget. The timer's own computation and cancellation are separate and conform to the established limit. No evidence supports a timer defect, lost tool call due to the deadline, or provider stop being misreported as a normal Agent completion.
