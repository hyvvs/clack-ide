Before the fix, the current clone loaded **1495→1496** with one needless commit, deleting only `null` optional inventory observations and advancing revision. A second load held 1496. After the fix the same clone loaded **1495→1495**, **zero CAS**, both loads stable. The retained backup likewise loaded **1494→1494**, **zero CAS**. The task branch has focused tests for current and historical startup, second-load idempotence, native `null` observations, harmless unknown top-level and nested fields, ordinary permissions, Fabric identities, positive and failed receipts, LM6 history, native atomic persistence delegation, concurrent edits/conflicts, and real recovery versus no-op peer-task startup. **Settings/qualification tests: 59/59 PASS; peer-task tests: 29/29 PASS; TypeScript typecheck PASS.** Original native B03 atomic/crash-recovery acceptance remains historical separate evidence; tests in this task do not fabricate a new physical B03 acceptance run.

## Real no-user-action Windows native verification

Two pre-peer-fix startup/normal-close cycles using the first fixed settings-only release (`980046f093532d233b84d9a82cdfeff9a45092e1bcfc8d2b692084895d5c3de5`) showed canonical revision **1495→1497→1498**: the first changed only native probe observations/profile timestamps/revision and the second only offline inventory `observedAt`/revision. Both processes exited through genuine WindowPattern.Close; shutdown itself did not write canonical settings. Those runs exposed the independent no-op peer-ledger revision issue and are **not** relabeled clean overall.

After the additional peer recovery fix, the exact **final** freshly built Windows release was `src-tauri/target/clack-startup-integrity-20261121/release/clack.exe`, SHA-256 **`de9b0da4124054ea929cdf1705caa89f0ea9b5af0f46adb8ea03dbc1c5788496`**. Original Tauri release command exited **0** in the isolated target root. Two genuine new native processes **3856** and **37728** were launched with **no UI mutation** and closed normally. Canonical settings moved **1498→1500→1501**, retaining **113,044 bytes** and exactly the protected authority; all differences were native probe observation timestamps and their revision counters. The native backup rotated to the preceding valid revision under unchanged atomic ownership. No Coder/Architect permission, selected model configuration, Fabric host/runtime/artifact/deployment identity, qualification receipt, LM6 record, or B03 authority changed.

The decisive in-memory before/after audit of parsed agent store, space store, peer ledger, canonical settings, native backup and window state **never saved raw JSON values to evidence**. It proved:

- `clack-ai-peer-tasks.json`: **byte-identical across both final launches**, revision **196**, zero tasks and zero gratuitous CAS.
- `terax-ai-agents.json`: first launch **reordered-only**, second **byte-identical**; permission authority unchanged.
- `terax-spaces.json`: **reordered-only** on both launches, no semantic workspace/tab changes.
- `.window-state.json`: first launch **byte-identical**, second **reordered-only**.
- Canonical self-hosted settings: only timestamp/observation and revision paths changed. Native offline retry is **30 seconds**; its observedAt updates on subsequent stale startup are **intended persisted runtime metadata**, not a write-on-read migration, and full byte-idempotence of these time-derived caches is **not** claimed.

A matched final production inventory recorded **9,670 BEFORE → 9,681 AFTER**, **0 read errors**, **57 differences**: **52** WebView2 cache/state files, **one** Clack diagnostic log, **one** native atomic backup rotation, **one** canonical settings file with the above bounded probe metadata, and **two** reordered-only agent/space store files. No unexplained semantic authority mutation was found in the final native run. The **five** scoped WinCred metadata fingerprints and **five** scoped secret blob hashes were identical BEFORE/AFTER. This is scoped to configured Clack/Terax AppData and HKCU registrations, not the entire OS.
