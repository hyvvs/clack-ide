## LM7: history remains a view, never permission authority

`buildDeploymentEvidenceHistory` reconstructs a transient read-only index from the existing native-CAS `fabric.qualificationReceipts` (at most 128 records) and `fabric.measurementRuns` (at most 48). There is **no second persistent index**, unbounded transcript or duplicate provider evidence. Each compact event retains its exact deployment/configuration, host, runtime/version/process/epoch, artifact digest, procedure/revision, timestamp, original verdict and failure class, evidence source/reference and typed Measured/Derived/Estimated/Unknown values. The historical LM6 attempt result is retained separately from a user-facing Incomplete conclusion when native correlation was missing.

`Current` requires the fresh independently verified exact runtime process, artifact, context and procedure scope. `Stale` is previously real proof no longer authorized under the present scope; `Historical` is superseded yet still preserved. Independently recorded `Failed`, `Incomplete`, `Unsupported`, `Verified`, `Passed` and `Cancelled` remain distinct. A later failed LM2F receipt revokes earlier PASS including ties at the same millisecond. LM2F v1 stays historical-only; unknown future receipt formats never grant access. Context-specific instruction or schema proofs cannot be marked current without corresponding current persona/schema context. For LM6, the newest **exact-current** run is selected even if a newer saved run from another epoch exists; all old runs remain visible. Cold/warm observations remain time-ordered with provenance, run reference and sample counts. Small samples are labeled bounded observations, not robust benchmarks.

Existing ledgers bound retention: this UX neither expands those limits nor purges failures. In the future, indefinite retention would need an explicit export/archive product, not an unbounded settings blob.

## LM10: deterministic, gated recommendations

The pure catalog and recommendation logic call existing LM2F `assessDeploymentCapability` / `assessDeploymentAgentEligibility`, `observedManagedFabric`, LM3–LM5 `assessDeploymentSuitability` and the exact LM6 `deploymentMeasurementPanel`. Categories: Chat, Coding, Low latency, Long context, Structured Output, Native Tools, Automatic Agent, This PC and Connected hosts. Every category requires currently Ready, exact-scope LM2F Chat qualification and non-insufficient workload fit. Coding/long-context require independent instruction evidence; long-context also requires configured context of at least 8192; structured output/native tools need their own current protocols; Automatic Agent requires independent instruction and *all* tool/effect gates; Low latency needs completed **current** measured warm Chat output. Stale speed cannot authorize a winner. If multiple speed candidates lack like-for-like scopes, no fastest model is asserted.

After mandatory gates, ties are resolved deterministically using current measured provenance, confidence, resource suitability and fit, comparable current warm latency where valid, measured normal Chat reliability, and lexical deployment ID. Locality is never a hidden preference except in the explicit This PC category. Every winner includes explanation, confidence, limitations, evidence references and alternatives. With no eligible candidates the result is **No currently qualified deployment**, never a fabricated least-bad recommendation. Recommendation evidence references include current authoritative records only; the history separately retains stale failures and prior runs.
