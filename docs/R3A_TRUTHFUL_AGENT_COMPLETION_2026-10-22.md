## Production changes and authority boundaries

- `todos.ts::terminalizeTodos` retains original accepted per-item states for **all** run terminal outcomes. The durable `SessionRun.state` and its original budget/error remain authoritative for stopped/restarted/cancelled runs; a failed *run* does not rewrite an unfinished *obligation* as failed. `todoStore` persists the same accepted list in its existing store, with no new memory database.
- `runObligations.ts::inspectRunObligations` is a **derived, bounded, read-only projection** of the current session's accepted Todos, its real UI-message tool-result parts, the owning workspace's existing PeerTask states, last model/answer finish and newer exact user instructions. The contract defines `not-started`, `in-progress`, `completed-unverified`, `verified-complete`, `failed`, `blocked` and `superseded`, but **current Todos cannot independently prove supersession**: a legacy `cancelled` item is conservatively `blocked`, not silently declared superseded. No unknown prose is parsed into synthetic requirements. Missing plans, user corrections not yet reconciled with the accepted plan and absent independent validation remain `unverified`.
- Native `write_file` successful *tool receipts* count as historical file effects, **not** functional feature or source-freshness validation. Bounded standalone `npm test`/`npm run build` native `bash_run` output, including exit code and timeout, is shown as a **historical check** only; subsequent observed source writes/edits mark earlier passing checks stale. Arbitrary shell strings, textual pseudo-tools, model claims, unrecognized command outcomes and opaque tool failures cannot become a passing check. Actual per-file/workspace freshness still requires an independent revision witness; shell-side mutations and missing native output may be invisible, so **even an observed passing command never itself marks a Todo verified**.
- `ScopedObligationProof` is a narrow *trusted-verifier-only* input: matching Todo ID, conversation, workspace, run start, user-turn count and **current** source/checkout revision, plus independently observed pass/fail. Only a completed Todo with matching passed proof and no unreconciled later user instruction becomes `verified-complete`; mismatched/failed/outdated proof never promotes success. **No production native verifier supplies this proof yet**: the positive proof test is an injected *contract fixture*, not a real application validation result. The live panel intentionally claims no verified-complete obligations until an actual verifier is wired; this is an R3b dependency.
- PeerTask records are filtered by source conversation, workspace and current-run creation boundary; a PeerTask `completed` result remains a **claim**, not test or current-source proof. Failed/blocked/unresolved related tasks are reported. The existing `continuationOnly` recognition is reused for retaining the **exact later substantive user correction** across repeated `Continue` and model-switch/compacted-history scenarios. No fabricated 50-to-25 semantic rewriting of an older plan occurs: the older plan needs explicit reconciliation before its completion can be certified.
- `RunObligationStatus` renders a readable *non-model-generated* status and up to eight unfinished Todos with historical build/test statuses, tool failures, source receipts, related PeerTasks, exact later instructions, recorded terminal cause and truthful availability of the **existing** Continue/Retry/explicit-limit controls. It is wired into the ordinary `AiChat` run surface for stopped/paused runs and explicitly hydrates persisted Todos when a finished conversation is opened after restart (the running-only `TodoStrip` is not mounted then). During hydration it reports loading, **not an empty accepted plan**, and selects the run-captured workspace identity when present. Transcript tool receipts/checks are labeled **historical conversation observations**, which can span multiple runs; they cannot certify current-run or checkout ownership. It neither triggers new tools/inference nor rewrites persisted messages or protected context.
- **No change** to Ollama, F1, provider wire format, prompt parsing/unsafe pseudo-tools, model names, context/output/deadlines, action/permission authorities, run step limits, effect retry behavior, PeerTask registry, local/remote transport or P2 platform features.
