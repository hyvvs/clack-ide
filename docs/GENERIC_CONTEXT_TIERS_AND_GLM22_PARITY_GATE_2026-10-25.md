## A. Production context-selection fix

**Code commit:** `6fb858e307940cf5db58e11f8543721d95d67713` (`fix: choose smallest safely verified Ollama runtime context tier`). The previous `contextBudgetProfile.ts` and `requestPreflight.ts` path used the trusted calibration **highest** directly as every Ollama `num_ctx`, even for small requests. The fix adds `minimumSafeContext.ts`, integrates it in `requestPreflight.ts`, changes native IPC final-byte serialization in `proxyFetch.ts`, and keeps context calibration trust sound after a *verified* lower per-request load in `contextCalibrationTrust.ts`.

1. Keep the *entire* final SDK-serialized system/history/assistant/tool-result/native-tool-schema request intact. First validate the original captured Ollama route and existing full request budget. The requested `num_predict` and full effective output reserve remain unchanged.
2. Only when the self-hosted Ollama profile is eligible, there is no manual `workingContext` pin, this is not a calibration probe or exact-context Agent logical continuation, and the original serialized `model` and `num_ctx` match the captured target: obtain the sorted, actual **successful** calibration attempts. Each usable candidate must have requested=loaded=context and a full fresh `snapshotContext` proof (digest, endpoint/revision, runtime epoch/version, allocation, expiration, reasoning, live instance and inventory).
3. Evaluate candidates ascending against the **same production `resolveContextBudget`** with complete serialized system and messages (including all conversation, tool effects, and tool schemas), full output cap/reserve and conservative margin; honor provider, output, configured and advertised ceilings. The first fully fitting tier wins. Missing, failed, unverified, stale, overflowing or unproven tiers never count.
4. **Native-tool caveat:** for a tool-bearing request, each proposed lower tier must additionally have *currently eligible native-tool verification for that exact context and captured reasoning choice* via `automaticAgentRecommendation`. Never borrow a 65K native tool proof for 32K. Continue to validate that tool proof, cancellation, approvals, and request identity in the normal path. A manually pinned or proof-unavailable request keeps the original trusted allocation; no fallback to an unverified smaller tier.
5. If eligible, change **only** `options.num_ctx` in the already measured final request and send that exact rewritten JSON through the existing native IPC path. Revalidate current settings, entire budget at the chosen smaller allocation, tier trust, tool proof and route **before dispatch**. A live loaded smaller per-request tier only retains the trusted higher *ceiling* when the probe reports an exactly requested and loaded *previously verified tier* and a real new allocation; unrelated allocation drift continues to invalidate context trust. Native postflight observation uses the actual selected context.
6. No required history or native tool result is dropped to fit a tier. If the unchanged request exceeds all qualifying tiers, leave the original fail-closed budget refusal intact. Answer/Agent continuation remains pinned to its own captured proof/context.

**GLM example:** 15,710 actual provider input + 8,192 output = 23,902 tokens before estimator margin; 16K is insufficient and 32K can fit if the actual Clack conservative serialized estimate also fits. This is an *illustrative* recorded token count, not an exact reconstruction of the final serialized wire. GLM's historical native tool proof was only verified at 65K. Thus **this fix by itself does NOT make that particular tool-bearing 65K Agent turn run at 32K**. Achieving that would require separate, fresh, exact-32K native-tool verification under the unchanged security predicates, not a silent proof transfer. This limitation is intentional and important.
