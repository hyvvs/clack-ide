## Owning check, lifecycle and alternative causes

1. **Frontend production request construction:** `src/modules/ai/lib/agent.ts` builds the captured model using the normal `createRequestPreflight` middleware and Ollama adapter. `requestPreflight.ts` `transformParams` refreshes self-hosted metadata, computes `runtimeTarget()` from `profileBudgetLimits()`, and sets Ollama `providerOptions.ollama.numCtx`. The serialized SDK Ollama body is passed through `proxyFetch.ts` to `preflight.prepare()` **before** `ai_http_open` and Rust/native `ai_http_stream`.
2. **Exact rejecting comparison:** after a second `refresh()` and `assertRequestBudget(...)`, the production preflight tested `(body.model !== captured modelId) || (body.options?.num_ctx !== runtimeTarget())`. Both comparisons use strict JavaScript equality, so `undefined` trusted target versus numeric wire context is a rejection. The R5 `ollama-context-route` code proves this comparator fired. **It does not identify which side differed** because the old message did not include either operand. No native/provider 400 was involved.
3. **Trust and revisions:** `contextBudgetProfile.ts` derives target from manual pin or (for this saved verified profile) `snapshotContext()`/`trustedContext()`; the latter requires matching model digest, endpoint configuration revision, native runtime epoch/provider version, provider-reported loaded context/allocation, reasoning identity, fresh evidence and nonexpired calibration. `contextRuntimeClient.ts` caches the native epoch/version only **30 seconds** and refreshes through `self_hosted_context_runtime`; `selfHostedProbe.ts` uses 30-second runtime-evidence freshness. Thus a lost, expired or temporarily unavailable trusted runtime record can make a target unavailable even while a recent Ollama `/api/ps` reports 65K; **R5 did not record an actual trust loss at the failing comparison**, so this is a bounded candidate, not a proven R5 cause. `budgetIdentity()` separately rejects a changed endpoint `configurationRevision`, model/digest or material working-context recommendation; harmless alias/performance guidance is treated differently. Native `self_hosted_context_runtime` acquires configured endpoint identity, observes `/api/version`, checks the saved config again, and publishes process epoch; this isn't a direct source for a different model string.
4. **Transport:** the endpoint was direct loopback `http://127.0.0.1:11435`, with `ssh:null`, so Clack's managed SSH reconnect/lease machinery was not on the Ollama Agent data path. In normal cases `remoteConnection.ts` acquires an SSH lease only for `clack-ssh.invalid` URLs, and remote native context runtime acquisition is a separate metadata operation. No evidence of remote host-key, tunnel replacement, configuration mutation or transport failure in R5.
5. **Harness:** the hidden native Tauri acceptance host used actual Clack Agent/SDK/proxy/preflight and real Ollama requests, not a mock transport; isolated `terax-settings.json` had same selected model/digest and `overrides:{}`. A harness-only race is **not established**; R3d full packaged Clack GUI and restart is still BLOCKED. The R5 harness recorded only **provider-dispatched** request bodies, not rejected pre-dispatch inputs. This is an instrumentation gap, not permission to invent a later `inference-18`.

**Attribution:** error creation is **Clack frontend TypeScript `requestPreflight.prepare`**, not Rust's `ai_http_stream`, provider HTTP, model text/tool parser, SSH manager, or Automatic reasoning selector. The broader root cause of why the comparator fired remains **UNRESOLVED**: a legitimate serialized mismatch, trust freshness transition between middleware serialization and preflight, or other request construction/configuration lifecycle difference all remain possible. That is not a model-quality verdict or a confirmed generic production bug.
