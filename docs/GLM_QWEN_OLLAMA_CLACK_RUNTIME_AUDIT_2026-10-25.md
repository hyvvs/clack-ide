## Provider generation during the two previous timeout events: critical reinterpretation

Both preserved Agent receive traces showed real native chunks successfully IPC-forwarded with **zero drops**, then ~60 seconds without more provider bytes, no Ollama done/EOF, no WebView2 crash.

* Qwen3.6 historical final request `inference-13`, local time ~02:49–02:50. Ollama runner log `task 511`, `n_ctx_slot=65536`, input **7,625 tokens**, continued printing `n_gen` through **744** at **~12.58 tokens/sec** until the HTTP request was cancelled at exactly 60 seconds. Native Clack observer last saw 8 chunks / 1,227 bytes ~60s before timeout.
* GLM historical final request `inference-22`, local time ~03:13–03:14. Runner log `task 9138`, `n_ctx_slot=65536`, input **15,710 tokens**, continued printing generated tokens through **2,593** at **~43.05 tokens/sec**. The HTTP connection ended at one minute and Ollama logged `srv stop: cancel task`, not generation completion. Native observer last saw 11 real chunks / 1,694 bytes, no drops, ~60 seconds earlier.

**These were NOT dead engines during the observed silent intervals.** The remote runner was computing until the Clack request cutoff. The traces **do not** establish whether either original provider request would have emitted a later chunk or completed: its serialized raw Coder request body (system/messages, 18 real tool JSON schemas and tool-state serialization) was deliberately **not retained** by the safe acceptance auditor, which stores only model/context/output/tool metadata. Do not misrepresent a substitute as an exact `inference-13` or `inference-22` replay.

## Exact Clack timeout, stream progress, and cancellation

`src-tauri/src/modules/net/inference/mod.rs` `Timeouts::for_policy(Policy::SelfHosted)` hardcodes **connect 10 s**, **first output 120 s**, **idle 60 s**, **overall 600 s**. The underlying Rust `Progress::feed` parser in `progress.rs` resets the rolling idle deadline only on **meaningful native stream JSON**: nonempty content, thinking, true tool calls or recognized equivalent provider deltas. Receipt of HTTP headers, raw no-op chunks, WebView heartbeat, ongoing provider generation that produces no streamed bytes, and unrelated progress do **not** reset it. `guarded()` uses Tokio biased select for cancellation/deadline; when timeout expires, the reqwest bytes stream future is dropped, Clack emits `phase=timed-out`, SDK gets `stream-idle-timeout`, and the server sees the client disconnect as task cancellation. Historical journal proves both provider tasks were cancelled while generation was still active. `src/modules/ai/lib/inferenceCalibration.ts` has an idle recommendation field, but this Rust self-hosted timeout is fixed by `for_policy` and the Tauri `ai_http_stream` API does not accept a profile-configurable idle duration.

`src/modules/ai/lib/contextBudgetProfile.ts` resolves fresh `snapshotContext` (highest trusted calibration target) to `workingTarget` and then to `runtimeTarget`; `src/modules/ai/lib/requestPreflight.ts` sets `providerOptions.ollama.numCtx = runtimeTarget()` and fail-closed compares the serialized context against the trusted target. The actual per-turn cost is **a fit gate**, not a candidate-specific minimum-allocation selector. Thus GLM's Agent sent **65,536** for all 15 coding turns because 65K had qualified, **not** because every turn used or needed 65K. There is no arbitrary override and trust verification is valid; the allocation is simply expensive for the observed load.

## Questions A–F and recommendations (no implementation)

**A. Yes, 65K materially increases reserved GPU KV and CPU weight overflow**, though it did not induce swap-outs or GPU OOM in these measurements. f16 GPU KV rises 846 -> 1,692 -> 3,384 MiB; host fit rises ~4.5 -> 5.5 -> 7.2 GiB and GPU generation drops from ~55.3 to ~48.6 tokens/sec on the controlled short input.

**B. Not proved.** All completed direct controls continuously streamed data with largest gap **4.851 seconds**. There is **no direct-provider success** yet after a >60-second stream silence.

**C. Yes, a premature cancellation of ongoing inference is strongly supported**, NOT the prior assertion of a dead/stalled model engine. Both Ollama runners kept generating internal tokens until Clack's fixed idle deadline and then logged cancellation. Whether they would have produced complete native responses cannot be proven from the saved redacted requests; a one-off truly equivalent full 18-schema/history provider reproduction would still be needed before claiming successful completion beyond 60 seconds.

**D. 16K is insufficient for GLM's exact final Agent input + full output reserve; 32K looks adequate but must pass Clack's conservative *complete* request fit.** Runner saw **15,710 input tokens** plus **8,192 reserved output** = **23,902**; adding 10% input margin gives ~**25,473**, under 32,768, over 16,384. This is a numerical feasibility check, **not** authorization to drop tool schemas or messages, and estimates must include the exact actual request, safety/system tool state and any unmeasured overhead. Qwen's recorded final input was ~7,625, but its full 8K output and conservative margin might fit 16K only after exact sizing. No experimental compaction was performed.

**E. Not an acute swap/parallelism crisis; there is reasonable tuning headroom.** Single concurrent slot and one loaded model are appropriate on 16 GB; keep those limits. Actual Flash Attention mode is `auto` (not proved off). f16 KV at 65K consumes 3,384 MiB; a future **separately authorized**, verified compatibility/performance/accuracy comparison of Flash Attention on and a supported quantized KV type such as `q8_0` could free capacity for expert weights, but do not change service environment speculatively. The first high-value runtime optimization is a smaller, **proven safe per-turn context**.

**F. Yes.** Code path pins the highest verified 65K allocation for every request and preflight checks it; it does not dynamically request the smallest verified context that preserves the full request and output margin.

**Recommended future generic Clack design, not implemented:** retain fresh digest/epoch/loaded-allocation proofs for *multiple qualified targets*, choose the **smallest verified context** that fits all actual system/user/assistant/tool messages + 8,192 output + conservative margin for that turn, block rather than truncate if none fits; ensure continuation preserves the original exact request/effects/permissions. Add model-neutral inference-progress diagnostics and a bounded self-hosted timeout policy that does not mistake unstreamed but active native tool/reasoning generation for a dead backend. Avoid blindly raising all timeouts: independently demonstrate a tool-bearing native provider response that **completes after >60 seconds of silence**, then regression-test timeout/deadline, cancellation, native scopes, output limits, verified tools and stalled-provider fail-closed behavior before changing production. A simple fixed universal 60s increase without completion proof is not justified by the present surrogate controls.

**Another acceptance mission? NO NOW.** The prior Qwen and GLM missions were terminally interrupted while servers were active, so **one** new independently frozen acceptance mission **per candidate could be warranted only after** an independently evidenced generic fix invalidates the original timeout outcome, regressions pass, and the user separately authorizes it. Neither model has passed notes acceptance. No reruns, new models, ForgeBoard, production Clack patch, Ollama service tuning or hardware changes were performed in this audit.
