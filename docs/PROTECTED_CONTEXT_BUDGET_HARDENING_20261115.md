## Protected-unit and history policy audit

The persisted campaign source has one original ForgeBoard user message and a canonical assistant message containing **22** SDK `step-start` markers, **22** settled tool calls, and 18 reasoning parts. Tool types: nine `write_file`, five `create_directory`, two `todo_write`, three `bash_run`, and one each of `list_directory`, `read_file`, and `edit`. The two historical failed commands include PowerShell `&&` syntax and an `ETARGET` dependency version; neither result proves successful work. The latest plan (step 14) is still authoritative, and the prior acknowledged complete-plan pair (step 2) is **already** retired by `currentPlanSteps(extra)`. The first plan cannot be counted again as new savings. The original mission text matches the frozen campaign-06 user objective at SHA-256 `f97ec34eefa136ac5be5847187f768b64bf5587d36140d9fcc53b695fa3e4801`.

`compactionPlan.ts:groupCompactionUnits` protects original user/system/attachment units, approvals, unresolved/failed tool effects and the latest successful plan, and keeps complete tool pairs together. It retains a token-sized 20% recent tail. `conversationCompaction.ts` already supports exact SDK `agentStep` splitting **for native-backed original sources**. By contrast, `agent.ts` supplies the current in-flight SDK steps through `prepare(extra)`, and `planCompaction` appends that `extra` without arbitrary lossy truncation. That is a concrete capacity limitation, but promoting transient extra into independently verified, native-backed original steps requires transaction-safe source promotion, append-only tail verification, native digest/coverage coordination and restart/permission safety. There is **no source-proof basis** to drop that history in this limited checkpoint merely to force admission. Leave this boundary fail-closed; preserve the complete tool output and write evidence.
